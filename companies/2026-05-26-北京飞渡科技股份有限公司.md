### ❓ 问题 1：Vue2 和 Vue3 的差异

- **问题描述:** 从响应式原理、性能、API 设计、生命周期、工程化几个角度，详细说一下 Vue2 和 Vue3 的差异。
- **我的解答:**
  这个问题我会分成五层来回答：**响应式、性能优化、代码组织、生命周期、生态能力**。

  1. **响应式原理不同**：
  - Vue2 基于 `Object.defineProperty` 对对象属性做劫持，需要递归遍历对象每个 key，因此对**新增属性、删除属性、数组下标修改、数组 length 变化**监听不够自然，常需要 `Vue.set()` 这类补充手段。
  - Vue3 基于 `Proxy` 代理整个对象，拦截更完整，不需要提前递归每个属性，天然支持对象新增删除、数组索引变化、`Map`、`Set` 等数据结构，响应式能力更强。

  2. **性能优化手段不同**：
  - Vue2 的模板编译和 diff 机制相对通用，更新时做的工作更多。
  - Vue3 在编译阶段引入了 **Patch Flag**、**静态提升**、**事件缓存** 等优化，运行时能更精准地知道哪些节点需要更新，因此渲染性能更好。
  - Vue3 还支持更好的 **Tree Shaking**，没有用到的 API 能在打包时被摇掉，最终包体积更小。

  3. **API 设计不同**：
  - Vue2 主要是 **Options API**，代码按 `data`、`methods`、`computed`、`watch` 拆开，业务逻辑分散在不同配置项里。
  - Vue3 除了兼容 Options API，还新增了 **Composition API**。它的优点是可以把同一功能逻辑聚合在一起，比如请求、监听、清理逻辑都放进一个 `useXXX()` 里，更适合复杂组件和逻辑复用。

  4. **生命周期命名有变化**：
  - Vue2 的 `beforeDestroy` / `destroyed`
  - Vue3 改成 `beforeUnmount` / `unmounted`
  - 本质含义接近，只是命名更统一，强调“卸载”概念。

  5. **工程化和 TS 友好度不同**：
  - Vue3 对 TypeScript 支持明显更好，类型推导、泛型、组合式函数的类型声明都更自然。
  - Vue3 还支持 `Fragment`、`Teleport`、`Suspense` 等新特性，在中后台、大屏、复杂弹层场景下更灵活。

  **总结：**
  Vue2 更适合历史项目和熟悉 Options API 的团队；Vue3 在性能、逻辑复用、工程化、类型支持方面更强，适合新项目和复杂业务。

- **知识点标签:** #Vue2 #Vue3 #响应式原理 #CompositionAPI

### ❓ 问题 2：你有用过 useXXX 和 Hook 吗？怎么封装、怎么用？

- **问题描述:** 你是否接触过 `useXXX` 这种封装方式？它和 Hook 的思想是什么？平时会怎么封装？
- **我的解答:**
  我主要用的是 **Vue3 Composition API 里的 `useXXX` 封装思路**，React Hook 我也了解它的思想，本质都是**把可复用的状态逻辑抽离成函数**。

  1. **为什么要封装 `useXXX`**：
  在传统写法里，请求、监听窗口变化、分页逻辑、表单逻辑会散落在 `data`、`methods`、`watch`、生命周期里，不利于复用。`useXXX` 的核心就是把一整块功能聚合起来，对外暴露状态和方法。

  2. **典型封装场景**：
  - `useRequest()`：统一管理 loading、error、data、重试
  - `usePagination()`：统一分页状态、页码切换、刷新
  - `useResize()`：监听窗口尺寸变化
  - `useWebSocket()`：统一连接、心跳、重连、消息分发

  3. **Vue3 中怎么封装**：

  ```js
  import { ref, onMounted, onUnmounted } from 'vue'

  export function useResize() {
    const width = ref(window.innerWidth)

    const handleResize = () => {
      width.value = window.innerWidth
    }

    onMounted(() => {
      window.addEventListener('resize', handleResize)
    })

    onUnmounted(() => {
      window.removeEventListener('resize', handleResize)
    })

    return { width }
  }
  ```

  使用时：

  ```js
  setup() {
    const { width } = useResize()
    return { width }
  }
  ```

  4. **React Hook 的理解**：
  React 里的 Hook 比如 `useState`、`useEffect`、`useMemo`，思路也是一样的。自定义 Hook 也是 `useXXX` 命名，把逻辑复用出去，只是 React 更依赖函数组件和 Hook 调用顺序规则。

  5. **封装时我会注意的点**：
  - 输入参数清晰，比如传 URL、初始值、配置项
  - 返回值稳定，比如统一返回 `data`、`loading`、`run`
  - 副作用一定要在卸载时清理，比如事件监听、定时器、WS、请求 abort
  - 不要把多个无关职责硬塞进一个 Hook，保持单一职责

  **一句话总结：**
  `useXXX` / Hook 的本质不是语法炫技，而是**逻辑聚合 + 状态复用 + 生命周期内聚**。

- **知识点标签:** #useXXX #Hook #逻辑复用 #CompositionAPI

### ❓ 问题 3：你有封装过 `v-` 指令吗？

- **问题描述:** 你有没有写过自定义指令？适合解决什么问题？和组件封装的区别是什么？
- **我的解答:**
  有，自定义指令适合处理**底层 DOM 行为增强**，比如权限控制、点击外部关闭、拖拽、水印、懒加载、自动聚焦这类场景。

  1. **什么时候用指令，不用组件**：
  - 如果只是增强某个 DOM 行为，比如给按钮加权限判断，这时候用组件反而太重，指令更轻量。
  - 组件更适合 UI 结构复用，指令更适合 DOM 行为复用。

  2. **我最常见的封装是按钮级权限指令**：

  ```js
  Vue.directive('permission', {
    inserted(el, binding) {
      const permission = binding.value
      const list = store.state.user.permissions
      if (!list.includes(permission)) {
        el.parentNode && el.parentNode.removeChild(el)
      }
    }
  })
  ```

  使用方式：

  ```vue
  <u-button v-permission="'user:delete'">删除</u-button>
  ```

  3. **还适合哪些场景**：
  - `v-debounce`：防抖点击
  - `v-lazy`：图片懒加载
  - `v-focus`：输入框自动聚焦
  - `v-watermark`：页面水印
  - `v-click-outside`：点击外部关闭弹层

  4. **封装指令时要注意**：
  - 在合适钩子里绑定和解绑事件
  - 避免内存泄漏
  - 尽量让指令职责单一，不要既做权限又做样式又做埋点

  **总结：**
  自定义指令本质上是对 DOM 行为的抽象，适合写“无 UI、强行为”的复用能力。

- **知识点标签:** #自定义指令 #Vue指令 #权限控制 #DOM

### ❓ 问题 4：uni-app 做 App 转译时会遇到什么兼容性问题？怎么解决？

- **问题描述:** uni-app 一套代码转 H5、小程序、App 时，经常会遇到兼容性问题。你实际遇到过哪些？怎么排查和处理？
- **我的解答:**
  这个问题我会从 **样式层、API 层、组件层、平台行为层** 四个方面回答。

  1. **样式兼容问题**：
  - 不同端对 CSS 支持程度不一样，比如某些 `flex` 细节、`position: sticky`、`overflow`、字体渲染效果，在 H5 和 App 上表现可能不同。
  - 解决方式是优先使用 uni-app 官方支持的样式能力，复杂样式做真机测试，并用**条件编译**处理差异。

  2. **单位和布局问题**：
  - `rpx` 在不同端表现并不完全一致，尤其涉及动态高度、键盘弹起、沉浸式状态栏时容易出问题。
  - 通常会统一封装尺寸换算函数，关键页面采用固定布局策略，减少依赖不稳定的自动适配。

  3. **原生能力和 API 差异**：
  - 比如文件上传、定位、相机、蓝牙、WebSocket、支付、文件系统等，在不同平台支持程度不同。
  - 解决方式是统一封装一层 API 适配层，业务代码不要直接散用 `uni.xxx`，而是走自己封装的方法。

  4. **组件渲染差异**：
  - 某些第三方组件在 H5 没问题，但转 App 后事件冒泡、滚动穿透、层级、弹窗遮罩会出现差异。
  - 解决方式是优先选跨端稳定的组件库，复杂组件自己二次封装，并且针对重点页面做多端回归测试。

  5. **性能和白屏问题**：
  - App 端首屏加载、长列表滚动、大图渲染、复杂动画容易比 Web 更敏感。
  - 解决方式包括：图片压缩、分页加载、虚拟列表、减少深层嵌套、按需渲染、启动阶段控制资源加载顺序。

  6. **排查方法**：
  - 先确认问题是业务代码、uni-app 框架、还是平台 WebView 差异
  - 用条件编译逐端缩小范围
  - 优先在真机调试，不完全依赖模拟器
  - 对高频问题沉淀一层统一适配

  **总结：**
  uni-app 的兼容性问题不可避免，核心不是“完全没有问题”，而是**通过封装、条件编译、真机回归和统一适配层，把差异控制住**。

- **知识点标签:** #uniapp #跨端兼容 #条件编译 #App开发

### ❓ 问题 5：前端如何做性能优化？

- **问题描述:** 如果让你从加载、渲染、请求、资源、代码结构几个角度系统性讲前端性能优化，你会怎么答？
- **我的解答:**
  我会按 **网络加载、渲染性能、代码层、工程层、用户体验层** 五块来答。

  1. **网络加载优化**：
  - 静态资源压缩，开启 gzip / brotli
  - 图片压缩、WebP、懒加载
  - 接口合并、分页加载、按需请求
  - CDN 加速、浏览器缓存、协商缓存

  2. **渲染性能优化**：
  - 长列表用虚拟列表或分页渲染
  - 减少不必要的响应式和重复渲染
  - 合理使用 `computed`，避免模板里写复杂表达式
  - 控制组件层级，减少深嵌套
  - 高频事件做防抖节流，比如 `scroll`、`resize`、输入联想

  3. **代码层优化**：
  - 组件拆分，避免单组件过大
  - 公共逻辑抽到工具函数或 `useXXX`
  - 合理使用 `keep-alive`
  - 及时清理定时器、监听器、未完成请求

  4. **工程化优化**：
  - 路由懒加载、组件按需加载
  - Tree Shaking
  - 打包体积分析，拆分 vendor 包
  - 生产环境去掉 sourceMap 或按需保留

  5. **用户体验优化**：
  - 骨架屏、loading、渐进式渲染
  - 首屏关键接口优先返回，非关键模块延迟加载
  - 对弱网和失败场景做降级处理

  **总结：**
  性能优化不是只看一个指标，而是从**请求更少、资源更小、渲染更快、交互更稳**四个方向系统去做。

- **知识点标签:** #性能优化 #前端工程化 #首屏优化 #渲染优化

### ❓ 问题 6：组件之间的 7 种通信方式

- **问题描述:** Vue 里组件之间怎么通信？如果让你系统说 7 种，你会怎么分类？
- **我的解答:**
  这个题我会按**父子通信、跨层级通信、兄弟组件通信、全局状态通信**来分类，常见 7 种如下：

  1. **`props` 父传子**：
  最基础、最常用的通信方式。父组件通过属性把数据传给子组件，适合单向下发数据。

  2. **`$emit` 子传父**：
  子组件通过 `$emit('事件名', 数据)` 通知父组件，实现事件上抛。通常和 `props` 配合使用，形成标准父子通信模型。

  3. **`v-model` / `.sync` 双向绑定语法糖**：
  本质还是 `props + emit`，只是语法上更方便。适合表单组件、弹窗显隐这类需要父组件感知子组件变化的场景。

  4. **`ref` / `$refs` 直接拿子组件实例**：
  父组件通过 `ref` 拿到子组件实例后，直接调用它的方法或访问其数据。这个方式适合调用子组件暴露的方法，比如打开弹窗、重置表单，但不适合大规模滥用，因为耦合会变高。

  5. **`provide / inject` 跨层级通信**：
  适合祖先组件和深层后代组件通信，避免 props 一层层透传。比如表单容器给深层字段组件下发统一配置、主题、注册能力。

  6. **事件总线 `eventBus`**：
  兄弟组件或无直接关系组件之间，可以借助一个公共事件中心通信，比如 `bus.$emit()` / `bus.$on()`。Vue2 中较常见，但大型项目里容易失控，所以更适合作为轻量补充方案。

  7. **Vuex / Pinia 全局状态管理**：
  适合多个页面、多个组件共享同一份状态，比如用户信息、权限、购物车、全局主题。它不是临时通信，而是把共享状态集中管理，是大型项目最稳定的方案。

  **如果面试官继续追问我会补一句：**
  - 父子组件优先用 `props + emit`
  - 跨层级优先 `provide/inject`
  - 多组件共享状态优先 `Vuex/Pinia`
  - `ref` 和 `eventBus` 能用，但不要滥用

- **知识点标签:** #组件通信 #props #emit #Vuex #provideInject

### ❓ 问题 7：插槽用过没？都有哪几种？怎么用？

- **问题描述:** Vue 里的插槽是什么？平时用过哪些类型？各自的适用场景是什么？
- **我的解答:**
  用过。插槽本质上是**父组件向子组件指定位置插入内容的一种机制**，可以提升组件的扩展性。

  1. **默认插槽**：
  子组件定义一个默认占位，父组件把内容塞进去。

  ```vue
  <!-- 子组件 -->
  <view class="card">
    <slot></slot>
  </view>
  ```

  ```vue
  <!-- 父组件 -->
  <Card>
    <text>这是默认内容</text>
  </Card>
  ```

  2. **具名插槽**：
  一个组件里需要多个可插拔区域，比如头部、内容区、底部。

  ```vue
  <!-- 子组件 -->
  <slot name="header"></slot>
  <slot></slot>
  <slot name="footer"></slot>
  ```

  ```vue
  <!-- 父组件 -->
  <Card>
    <template v-slot:header>标题</template>
    <text>正文</text>
    <template v-slot:footer>按钮区</template>
  </Card>
  ```

  3. **作用域插槽**：
  子组件不仅给父组件“坑位”，还把自己的数据暴露出去，让父组件决定怎么渲染。

  ```vue
  <!-- 子组件 -->
  <slot :row="row" :index="index"></slot>
  ```

  ```vue
  <!-- 父组件 -->
  <template v-slot:default="{ row, index }">
    <view>{{ index }} - {{ row.name }}</view>
  </template>
  ```

  4. **实际使用场景**：
  - 表格列自定义
  - 弹窗头部和底部按钮区
  - 卡片组件内容扩展
  - 列表项自定义渲染

  **总结：**
  插槽本质上解决的是“组件既有固定结构，又要保留可扩展区域”的问题。

- **知识点标签:** #插槽 #默认插槽 #具名插槽 #作用域插槽
