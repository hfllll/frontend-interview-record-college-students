### ❓ 问题 2：多表单联动 + 组件化，怎么做？

- **问题描述:** 一个页面有多个表单，彼此数据会相互影响（比如选 A 表单的某个值，B 表单的选项也会变），还要组件化方便后续新增表单类型。你怎么设计？
- **我的解答:**
  核心思路：**数据上提 + 事件下发 + 配置驱动**。

  1. **数据上提**：所有表单的共享数据统一放在父组件或 Vuex store 中，各子表单不各自维护独立状态，而是通过 props 接收、通过 `$emit` 或 `v-model` 回传变更。

  2. **配置驱动**：定义一份表单描述配置数组，每个表单子组件对应一个配置项，描述其类型、字段列表、校验规则、联动条件等。后续新增表单类型只需追加配置 + 注册一个新的子组件，不用改动父组件逻辑。

  ```js
  const formConfig = [
    { type: 'basic', fields: ['name', 'phone'], ref: 'BasicForm' },
    { type: 'advanced', fields: ['region', 'industry'], dependOn: 'basic', ref: 'AdvancedForm' },
  ]
  ```

  3. **联动逻辑**：在父组件中用 `computed` 或 `watch` 监听关键字段变化，计算衍生数据后通过 props 下发到受影响的子组件。复杂联动可抽象成规则引擎——配置 `{ sourceField, targetField, mapFn }` 规则表，统一处理。

  4. **子组件规范**：每个子组件暴露统一的 props 接口（`value` / `config` / `disabledFields`）和 events（`input` / `change`）。以此保证插拔式替换能力。

- **知识点标签:** #组件设计 #表单联动 #配置驱动 #Vue

### ❓ 问题 3：Web 端长列表怎么做性能优化？

- **问题描述:** 后端可能返回几百上千条数据，前端渲染时页面很卡，你怎么处理？
- **我的解答:**
  从渲染层面和策略层面两条线来优化：

  1. **虚拟滚动 / 虚拟列表**：只渲染可视区域内的 DOM 节点，滚动时动态替换。项目中我用过 `uni-app` 的 `recycle-view` 或 Web 端的 `vue-virtual-scroller`，把一次性渲染 1000 条减少到只渲染 10-15 条。

  2. **分页加载 / 滚动加载**：后端不做全量返回，前端用分页参数或 Cursor 做 `scroll` 触底加载，每次只拿 20-50 条。这个是最基础也最有效的方案。

  3. **避免不必要的响应式**：列表数据如果只是展示不做编辑，用 `Object.freeze()` 冻结数据，或存放到非响应式变量中，减少 Vue 的 getter/setter 劫持开销。

  4. **减少组件层级**：列表项尽量扁平，不用深层组件嵌套；`computed` 代替 `methods` 中的重复计算；`v-show` 代替频繁切换的 `v-if`。

  5. **图片懒加载**：配合 Intersection Observer 或 `uni-app` 的 `lazy-load` 属性，避免一次性发起大量图片请求。

- **知识点标签:** #性能优化 #虚拟列表 #长列表 #Vue

### ❓ 问题 4：列表有 7-8 种类型，一直 v-if 很重，怎么优化？

- **问题描述:** 一个列表里每条数据可能是不同类型（纯文本、图文、视频、卡片等），都用 v-if/v-else-if 链式判断会很臃肿且频繁 diff，你怎么做？
- **我的解答:**
  坦诚讲，**动态组件 `<component :is>` 本质上仍是条件渲染**——只是把 `v-if` 链换成了查表 `typeMap[item.type]`，Vue 内部依然要对每条数据决议渲染哪个组件，并没有从根上消除判断开销。

  真正"零条件决议"的做法是：**遍历前按 type 预分组，每组用固定组件直接渲染**。

  ```js
  computed: {
    grouped() {
      const map = { text: [], image: [], video: [], card: [] }
      this.list.forEach(item => map[item.type]?.push(item))
      return map
    }
  }
  ```

  ```vue
  <TextItemList  :items="grouped.text"  />
  <ImageItemList :items="grouped.image" />
  <VideoItemList :items="grouped.video" />
  <CardItemList  :items="grouped.card"  />
  ```

  **代价与取舍：**

  | 方案 | 条件判断 | 列表原序 | 适用场景 |
  |---|---|---|---|
  | v-if 链 | 每条数据判断 1 次 | ✅ 保持 | 类型 ≤ 3 种，懒得拆组件 |
  | `<component :is>` | 每条数据查表 1 次 | ✅ 保持 | 类型多但要求保序 |
  | **预分组 + 固定组件** | **零判断** | ❌ 同类型扎堆 | 不需严格保序，性能优先 |
  | 前端只负责渲染，后端按类型排好序返回 | 零判断 + 保序 | ✅ | 最佳方案，但依赖后端配合 |

  实际面试中我会先讲动态组件方案（保序是默认需求），再补充：**如果后端愿意按 type 排序返回，前端直接分组渲染，完全消除条件开销**——这个思路能体现你不仅会写代码，还会从链路层面做优化。

- **知识点标签:** #动态组件 #v-if优化 #组件设计 #Vue

### ❓ 问题 5：角色鉴权怎么做？到按钮级别。

- **问题描述:** 不同角色（管理员、普通用户、访客）看到不同的菜单和按钮，你是怎么实现的？细到什么程度？
- **我的解答:**
  分三层鉴权：**路由级 → 页面级 → 按钮级**。

  1. **路由级鉴权**：
  - 后端登录时返回该角色的**权限编码数组**，如 `['user:list', 'user:edit', 'report:view']`。
  - 前端路由配置的 `meta` 中声明所需权限码。`router.beforeEach` 中判断当前用户的权限集合是否包含目标路由的权限码，不满足则拦截或跳 403。

  2. **按钮级鉴权——自定义指令 `v-permission`**：

  ```js
  Vue.directive('permission', {
    inserted(el, binding) {
      const { value } = binding
      const permissions = store.state.user.permissions
      if (value && !permissions.includes(value)) {
        el.parentNode && el.parentNode.removeChild(el)
      }
    }
  })
  ```

  使用方式：
  ```vue
  <u-button v-permission="'user:delete'">删除</u-button>
  <u-button v-permission="'user:export'">导出</u-button>
  ```

  指令在元素插入 DOM 时校验权限，无权限则**直接移除 DOM 节点**，而不是隐藏——因为隐藏仍有被 devtools 打开的风险。

  3. **编码规范**：前端和后端统一权限码命名规范（`模块:操作`），新增功能时前后端同步注册权限码，放入统一的常量文件中维护。

- **知识点标签:** #权限控制 #自定义指令 #路由守卫 #安全性

### ❓ 问题 6：你的 WebSocket 是如何做单一管理的？

- **问题描述:** 多个页面/组件都要用 WebSocket，怎么保证全局只有一个连接，且各组件都能收发消息？
- **我的解答:**
  封装一个**全局单例 WS 管理器**，核心解决三个问题：实例唯一、消息分发、生命周期安全。

  1. **单例模式保证唯一性**：

  ```js
  class WsManager {
    constructor() {
      if (WsManager._instance) return WsManager._instance
      this.ws = null
      this.listeners = new Map()  // 按消息类型分发回调
      this.timer = null
      this.retryCount = 0
      WsManager._instance = this
    }

    connect(url) {
      if (this.ws && this.ws.readyState === WebSocket.OPEN) return
      this.ws = new WebSocket(url)
      this._bindEvents()
    }
  }
  ```

  2. **发布-订阅模式分发消息**：组件通过 `on(type, callback)` 注册监听，通过 `off(type, callback)` 销毁。服务端推送时 WS 管理器统一接收，再按消息 `type` 字段分发给所有订阅了该类型的回调。

  ```js
  // 组件 A 中
  wsManager.on('price_update', this.handlePrice)

  // 组件销毁时
  beforeDestroy() {
    wsManager.off('price_update', this.handlePrice)
  }
  ```

  3. **心跳保活 + 断线重连**：

  ```js
  _bindEvents() {
    this.ws.onopen = () => {
      this.retryCount = 0
      this._startHeartbeat()  // 每 30s 发 ping
    }
    this.ws.onclose = () => {
      this._clearHeartbeat()
      this._reconnect()  // 指数退避：2s → 4s → 8s，最大 5 次
    }
  }
  ```

  4. **全局唯一入口**：挂载到 `Vue.prototype.$ws = new WsManager()`，所有页面/组件共享同一实例。App.vue 的 `onLaunch/created` 中调用 `$ws.connect()` 统一初始化。

- **知识点标签:** #WebSocket #单例模式 #发布订阅 #状态管理

### ❓ 问题 7：页面或组件关闭时，我们会进行哪些操作？

- **问题描述:** 组件卸载或页面关闭前，前端需要做哪些清理工作？为什么这些操作不能省略？
- **我的解答:**
  核心原则：**拿走的资源要还回去，防止内存泄漏和僵尸回调**。主要清理这几类：

  1. **定时器**：`clearInterval` / `clearTimeout`。最常见的内存泄漏源，页面都关了定时器还在跑。

  2. **事件监听器**：通过 `addEventListener` 绑定的全局事件（scroll、resize、keydown 等），必须在 `beforeDestroy` 中用 `removeEventListener` 解绑。Vue 组件内部的事件会自动回收，但挂到 `window` / `document` 上的不会。

  3. **Observer 实例**：`IntersectionObserver`、`ResizeObserver`、`MutationObserver`，调用 `observer.disconnect()` 释放。

  4. **正在进行的请求——取消**：
  - uni-app：保存 `requestTask` 引用，`onUnload` 中调用 `requestTask.abort()`
  - Web 端 `fetch`：创建 `AbortController`，`controller.abort()`
  - axios：使用 `CancelToken.source`，`source.cancel('页面已卸载')`

  5. **发布订阅 / WS 监听**：调用 `wsManager.off('xxx', this.handler)` 或 `eventBus.$off('xxx')`，否则下次回来会重复注册回调，触发 N 次。

  6. **大对象引用置空**：列表数据、图片 base64 等大体积数据设为 `null`，帮助 GC 回收。

  实际在 `beforeDestroy` / `onUnload` 中写一个统一的 `cleanup()` 方法集中清理，代码习惯就是这样养成的。

- **知识点标签:** #内存泄漏 #生命周期 #资源清理

### ❓ 问题 8：组件进入后又马上退出，进行中的请求怎么办？

- **问题描述:** 用户快速点击，页面 A 刚进入发了请求，还没返回就切走了。如果不处理，请求回来后尝试 `setData` 到一个已销毁的组件，轻则控制台报错，重则数据污染。你怎么处理？
- **我的解答:**
  分场景、分层处理：

  1. **最直接——取消请求**：
  - uni-app：`requestTask.abort()`
  - fetch：`AbortController.abort()`
  - axios：`CancelToken` 或 新版 `AbortSignal`

  ```js
  // uni-app 示例
  data() { return { task: null } },
  onLoad() {
    this.task = uni.request({ url: '/api/data', success: res => this.list = res.data })
  },
  onUnload() {
    this.task && this.task.abort()
  }
  ```

  2. **不取消请求，但忽略回调——"请求版本号"方案**：
  适合同一个页面多次进出的场景（如 Tab 切换）。给每次请求打一个递增的 `requestId`，回调时比对当前页面版本号，旧的直接丢弃：

  ```js
  let currentId = 0
  onShow() {
    const id = ++currentId
    request().then(res => {
      if (id !== currentId) return  // 旧请求，忽略
      this.list = res.data
    })
  }
  ```

  3. **axios 拦截器统一处理**：在响应拦截器中判断当前路由是否仍活跃，配合上面的版本号或标志位，全局自动丢弃过期响应。

  4. **性价比最高的方案——防抖节流 + 路由守卫**：路由跳转前发一个全局 event，所有进行中的请求收到信号后自动 abort 或标记过期。不用每个页面单独写。

  **实际项目中**，uni-app 我习惯用 `requestTask.abort()` 直接取消，简单粗暴没副作用；Web 端复杂页面则用版本号方案，因为有些 POST 请求（如提交订单）是不能取消的。

- **知识点标签:** #请求管理 #AbortController #异步安全 #生命周期

### ❓ 问题 9：很多个请求，如何控制页面在第一个请求回来时就渲染？

- **问题描述:** 页面初始化同时发多个请求，但不需要等全部完成才渲染——哪个先回来就先渲染哪个，提升首屏体验。怎么做？更进一步，如果有一个请求是关键的、必须先渲染，其他可以慢，又怎么做？
- **我的解答:**
  分两层回答——**纯竞速** 和 **关键请求优先**：

  **1. 纯竞速——`Promise.race`**

  ```js
  Promise.race([
    fetchUserInfo(),
    fetchBannerList(),
    fetchProductList(),
  ]).then(firstData => {
    this.firstContent = firstData  // 谁先回来渲染谁
  })
  ```
  `Promise.race` 只有一个 winner，第一个完成的 promise 决定 then 的回调值。

  **2. 竞速但都要——各自独立渲染**

  实际场景更常见：给每个模块独立维护状态，各回各的、各渲各的，不互相阻塞：

  ```js
  onLoad() {
    fetchUserInfo().then(res => { this.user = res })
    fetchBannerList().then(res => { this.banners = res })
    fetchProductList().then(res => { this.products = res })
  }
  ```
  模板中用骨架屏占位，`user` 一回来用户信息区就显示，`banners` 没回来就继续展示骨架屏。**这是日常开发中最主流的做法**。

  **3. 关键请求先渲染——`Promise.allSettled` + 优先级**

  如果有一个请求是"门闩"——它不回来整个页面不能渲染（比如用户权限）——那就：

  ```js
  const critical = fetchPermission()  // 门闩请求
  const secondary = [fetchBannerList(), fetchProductList()]

  critical.then(permission => {
    this.permission = permission  // 关键数据先渲染，页面骨架立即可见
    // 次要数据陆续填充
    secondary.forEach(p => p.then(res => this.fillData(res)))
  })
  ```

  **总结：**
  - 纯竞速 → `Promise.race`
  - 独立模块各渲各的（最常用） → 各自 `.then`，骨架屏占位
  - 有关键门闩请求 → 先 `await` 关键，次要并发

- **知识点标签:** #Promise #异步渲染 #用户体验 #首屏优化

### ❓ 问题 10：你知道乾坤这个微前端框架吗？

- **问题描述:** 公司业务和微前端相关，所以追问你是否了解 `qiankun`，它主要解决什么问题，核心原理是什么，适合什么场景？
- **我的解答:**
  我知道，`qiankun` 是阿里开源的一套 **微前端落地框架**，可以把多个独立的前端应用组合到一个主应用里运行。它主要解决的是**大型系统多人并行开发、技术栈不统一、主子应用独立部署**这些问题。

  1. **它解决的核心痛点**：
  - 一个后台系统越来越大，多个业务线都往里加模块，最后变成单体巨石应用，构建慢、发布风险高。
  - 不同团队技术栈不一致，有的用 Vue2，有的用 Vue3、React，如果强行统一成本很高。
  - 希望每个业务模块都能**独立开发、独立测试、独立部署**，而不是每次都整包发布。

  2. **乾坤的基本思路**：
  - 有一个 **主应用**，负责注册子应用、路由分发、加载入口。
  - 各个业务模块作为 **子应用** 存在，本身可以单独运行，也可以被主应用接入。
  - 当路由切换到某个子应用时，主应用去加载它的 HTML、JS、CSS，并触发子应用的生命周期，比如 `bootstrap`、`mount`、`unmount`。

  3. **核心原理我知道几块**：
  - **基于 single-spa** 做应用注册和生命周期调度。
  - **JS 沙箱**：隔离子应用对 `window` 的污染，避免多个子应用互相覆盖全局变量。
  - **CSS 隔离**：防止样式串扰，常见方式是作用域隔离、样式前缀、Shadow DOM 等。
  - **运行时加载**：不是把所有子应用打进一个包，而是按路由动态加载。

  4. **适合的场景**：
  - 中后台系统特别大，多个团队长期并行开发。
  - 业务模块边界清晰，比如用户中心、订单中心、报表中心相对独立。
  - 需要历史项目渐进式迁移，比如老系统是 Vue2，新模块想用 Vue3 或 React。

  5. **不适合的场景**：
  - 小项目、团队人数少、业务边界不清晰时，上微前端反而会增加通信、部署、运维复杂度。
  - 如果只是为了“技术上高级”而上微前端，性价比不高。

  6. **如果面试官继续追问，我会补一句**：
  微前端不是银弹，它本质上是用架构复杂度换团队协作效率。只有当**项目规模、团队规模、独立部署诉求**都达到一定程度时，才值得引入。

- **知识点标签:** #微前端 #qiankun #single-spa #架构设计
