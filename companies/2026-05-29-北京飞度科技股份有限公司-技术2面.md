### ❓ 问题 1：HTML 的英文名和中文名全称是什么？

- **问题描述:** 说一下 HTML 的完整英文名和中文名。
- **我的解答:**
  HTML 的英文全称是 **HyperText Markup Language**，中文全称是 **超文本标记语言**。

  我对这个概念的理解是：
  - **HyperText（超文本）**：不只是纯文字，还可以通过链接跳转到其他资源
  - **Markup（标记）**：通过标签来描述内容结构
  - **Language（语言）**：它是一套描述网页结构的标准语言

  HTML 本身不是编程语言，它主要负责页面的**语义结构**，比如标题、段落、表格、表单、图片、链接等。

- **知识点标签:** #HTML #前端基础 #语义化

### ❓ 问题 2：CSS 能设置变量吗？

- **问题描述:** CSS 里能不能像 JS 一样定义变量？一般怎么用？
- **我的解答:**
  可以，CSS 原生支持变量，通常叫 **CSS 自定义属性**。

  定义方式：

  ```css
  :root {
    --primary-color: #409eff;
    --font-size-base: 14px;
    --card-padding: 16px;
  }
  ```

  使用方式：

  ```css
  .button {
    background: var(--primary-color);
    font-size: var(--font-size-base);
    padding: var(--card-padding);
  }
  ```

  补充几点：
  1. `:root` 下定义的是全局变量
  2. 也可以在某个类下面定义局部变量，只在当前作用域生效
  3. `var(--xxx, 默认值)` 可以设置兜底值
  4. 很适合做**主题切换**、统一设计规范、减少重复样式

  和 `scss/less` 变量的区别是：
  - 预处理器变量是**编译时**替换
  - CSS 变量是**运行时**存在，可以被 JS 动态修改

- **知识点标签:** #CSS #CSS变量 #主题切换

### ❓ 问题 3：UnoCSS 的运作原理是什么？

- **问题描述:** 你了解 UnoCSS 吗？它和 Tailwind 有什么类似点？底层是怎么工作的？
- **我的解答:**
  UnoCSS 本质上是一个**原子化 CSS 引擎**，核心思想是：**扫描代码中的类名，然后按规则即时生成对应的 CSS**。

  它的运作流程大致是：

  1. **扫描源码**
  - 扫描 `.vue`、`.tsx`、`.html` 等文件里的 class 名

  2. **匹配规则**
  - 比如扫描到 `text-red-500`、`m-4`、`flex`，就去规则表里匹配这些类名代表什么样式

  3. **生成 CSS**
  - 只生成项目里真正用到的样式，而不是预先生成一整套完整样式库

  4. **构建时注入**
  - 最终把这些生成出来的 CSS 注入到构建结果中

  它的优势：
  - **按需生成**，体积小
  - 生成速度快
  - 可扩展性强，可以自定义 `rules`、`shortcuts`、`presets`

  举个例子：

  ```html
  <div class="flex items-center text-red-500 p-4"></div>
  ```

  UnoCSS 会识别这些类，然后生成类似：

  ```css
  .flex { display: flex; }
  .items-center { align-items: center; }
  .text-red-500 { color: #ef4444; }
  .p-4 { padding: 1rem; }
  ```

  **一句话总结：**
  UnoCSS 不是提前提供一整套 CSS，而是**扫描到什么类，就生成什么样式**。

- **知识点标签:** #UnoCSS #原子化CSS #工程化 #构建原理

### ❓ 问题 4：CSS 类堆满了标签，很嘈杂怎么办？

- **问题描述:** 如果标签上的 class 写得特别长、特别多，看起来很乱，应该怎么优化？
- **我的解答:**
  这是原子化 CSS 常见问题，我会从 4 个方向优化：

  1. **抽 shortcuts / 语义化组合类**
  - 把经常重复出现的一长串类抽成一个短类名

  例如：

  ```ts
  shortcuts: {
    'flex-center': 'flex justify-center items-center',
    'card-box': 'bg-white rounded-lg shadow p-4'
  }
  ```

  使用时直接写：

  ```html
  <div class="card-box"></div>
  ```

  2. **组件化**
  - 如果某一块结构重复很多次，不要继续堆 class，直接封装成组件，把样式收进组件内部

  3. **按职责拆分**
  - 布局类、颜色类、状态类分组书写，至少让可读性高一点

  4. **复杂场景回归普通 CSS / SCSS**
  - 原子化 CSS 不适合所有场景
  - 如果某块样式逻辑非常复杂、状态很多、类太长，直接回到 `scss` 或 `module css` 反而更清晰

  **总结：**
  类太多时，不是硬堆，而是通过**shortcuts、组件化、语义化抽象**降低噪音。

- **知识点标签:** #CSS工程化 #UnoCSS #组件化 #样式管理

### ❓ 问题 5：Promise 的原理是什么？

- **问题描述:** 你怎么理解 Promise？它解决了什么问题？
- **我的解答:**
  Promise 本质上是 **对异步操作结果的统一封装**，主要解决的是**回调地狱**和异步流程难以管理的问题。

  它有三个核心点：

  1. **内部维护状态**
  - 初始是 `pending`
  - 成功变成 `fulfilled`
  - 失败变成 `rejected`

  2. **保存结果**
  - 成功时保存成功值
  - 失败时保存失败原因

  3. **发布订阅思想**
  - 调用 `then` / `catch` 时，相当于注册回调
  - 当异步任务完成后，Promise 会统一触发这些回调

  一个简单理解：

  ```js
  const p = new Promise((resolve, reject) => {
    setTimeout(() => {
      resolve('成功结果')
    }, 1000)
  })

  p.then(res => {
    console.log(res)
  })
  ```

  这里 Promise 做的事情就是：
  - 先接管异步任务
  - 任务完成后修改状态
  - 再执行对应回调

  **一句话总结：**
  Promise 就是一个**有状态、可链式调用、专门管理异步结果的对象**。

- **知识点标签:** #Promise #异步编程 #JavaScript

### ❓ 问题 6：Promise 有哪三个阶段？

- **问题描述:** Promise 的状态有哪些？
- **我的解答:**
  Promise 一共有三个状态：

  1. **pending**
  - 初始状态，表示进行中

  2. **fulfilled**
  - 操作成功，调用了 `resolve`

  3. **rejected**
  - 操作失败，调用了 `reject`

  示例：

  ```js
  const p = new Promise((resolve, reject) => {
    resolve('ok')
  })
  ```

  这个 Promise 会从 `pending` 变成 `fulfilled`。

- **知识点标签:** #Promise #状态机 #JavaScript

### ❓ 问题 7：Promise 的状态是否可逆？为什么？

- **问题描述:** Promise 一旦状态变化后还能改回去吗？为什么？
- **我的解答:**
  **不可逆。**

  原因是 Promise 的设计本身就是**单向状态机**：

  - 只能从 `pending` → `fulfilled`
  - 或者从 `pending` → `rejected`
  - 一旦状态确定，就不能再变回 `pending`
  - 也不能从 `fulfilled` 改成 `rejected`

  例如：

  ```js
  const p = new Promise((resolve, reject) => {
    resolve('success')
    reject('error')
  })
  ```

  最终只会认第一次的 `resolve('success')`，后面的 `reject` 会被忽略。

  这样设计的原因是：
  1. 保证异步结果的**确定性**
  2. 避免状态反复变化导致逻辑混乱
  3. 方便链式调用和错误传递

  **一句话总结：**
  Promise 状态一旦敲定就不可逆，这是为了保证异步流程稳定、结果唯一。

- **知识点标签:** #Promise #状态不可逆 #异步编程

### ❓ 问题 8：如果有 1000 个请求，每一个都依赖上一个请求的结果，该怎么做？

- **问题描述:** 有一串接口调用，后一个请求必须依赖前一个请求返回的数据，这种顺序请求怎么处理？
- **我的解答:**
  这种场景本质上是**串行异步任务**，不能并发，只能一个接一个执行。

  最直接的写法是 `async/await`：

  ```js
  async function runTasks(tasks) {
    let prevResult = null

    for (const task of tasks) {
      prevResult = await task(prevResult)
    }

    return prevResult
  }
  ```

  如果 `tasks` 是 1000 个请求函数，每一个都接收上一次结果作为参数，就可以这样串起来。

  示例：

  ```js
  const tasks = [
    (prev) => requestA(prev),
    (prev) => requestB(prev),
    (prev) => requestC(prev),
  ]

  runTasks(tasks)
  ```

  如果面试官继续追问，我会补两点：

  1. **不能用 `forEach` + await**
  - 因为 `forEach` 不会等待异步完成

  2. **如果 1000 个全串行太慢**
  - 说明业务设计可能有问题
  - 可以考虑是否真的全部强依赖，能不能拆成“分组串行、组内并发”

  **一句话总结：**
  上一个结果驱动下一个请求，本质就是**串行 Promise 链**，推荐 `for...of + await`。

- **知识点标签:** #Promise #asyncAwait #串行请求 #异步控制

### ❓ 问题 9：Set 和 Map 的区别是什么？

- **问题描述:** ES6 里的 Set 和 Map 分别用来做什么？区别在哪？
- **我的解答:**
  它们都属于 ES6 提供的新数据结构，但用途不同：

  1. **Set**
  - 类似数组，但成员**不能重复**
  - 常用来做**数组去重**

  ```js
  const s = new Set([1, 2, 2, 3])
  console.log([...s]) // [1, 2, 3]
  ```

  2. **Map**
  - 类似对象的键值对结构
  - 但它的 key 可以是**任意类型**
  - 比普通对象更适合做真正意义上的映射关系

  ```js
  const m = new Map()
  m.set('name', 'Tom')
  m.set({ id: 1 }, 'obj value')
  ```

  核心区别：
  - Set 存的是**值**
  - Map 存的是**键值对**
  - Set 用于去重、成员集合
  - Map 用于映射、缓存、关联关系

- **知识点标签:** #ES6 #Set #Map #数据结构

### ❓ 问题 10：Vue2 和 Vue3 的区别

### ❓ 问题 11：`reactive` 和 `ref` 的区别

- **问题描述:** Vue3 里 `reactive` 和 `ref` 有什么区别？
- **我的解答:**
  核心区别有三点：

  1. **适用数据类型不同**
  - `ref` 可以包基本类型，也可以包对象
  - `reactive` 只能包对象、数组这类引用类型

  2. **访问方式不同**
  - `ref` 要通过 `.value`
  - `reactive` 直接通过属性访问

  ```js
  const count = ref(0)
  const state = reactive({ count: 0 })

  console.log(count.value)
  console.log(state.count)
  ```

  3. **解构影响不同**
  - `reactive` 解构后容易丢失响应式
  - `ref` 更适合在组合式函数中单值返回

  实际使用中：
  - 单个值用 `ref`
  - 一组相关状态用 `reactive`

- **知识点标签:** #Vue3 #ref #reactive #CompositionAPI

### ❓ 问题 12：`computed` 和 `watch` 的区别

- **问题描述:** 这两个都和响应式有关，它们分别适合什么场景？
- **我的解答:**
  它们的定位完全不同：

  1. **computed**
  - 用于**基于已有数据派生新值**
  - 有缓存
  - 只有依赖变化时才重新计算

  ```js
  const fullName = computed(() => firstName.value + lastName.value)
  ```

  2. **watch**
  - 用于**监听某个值变化后执行副作用**
  - 适合做请求、日志、定时操作、联动处理

  ```js
  watch(keyword, (newVal) => {
    fetchSearchList(newVal)
  })
  ```

  **一句话总结：**
  - `computed` 是拿来“算值”的
  - `watch` 是拿来“做事”的

- **知识点标签:** #Vue3 #computed #watch #响应式

### ❓ 问题 13：监听值的变化并执行函数，用哪个？为什么？

- **问题描述:** 如果我要监听一个值变化后执行函数，应该选 `computed` 还是 `watch`？
- **我的解答:**
  应该用 **`watch`**。

  因为你的目标不是得到一个新的计算值，而是想在值变化后**执行某个操作**，这就是典型的副作用场景。

  比如：
  - 输入框内容变化后调搜索接口
  - 路由变化后重新拉数据
  - 表单值变化后做联动处理

  示例：

  ```js
  watch(
    () => formData.type,
    (newVal, oldVal) => {
      console.log('类型变化了', newVal, oldVal)
      fetchOptions(newVal)
    }
  )
  ```

  为什么不用 `computed`：
  - `computed` 设计目标是返回一个新值
  - 它不适合承载请求、日志、DOM 操作这类副作用逻辑

- **知识点标签:** #watch #computed #副作用 #Vue3

### ❓ 问题 15：Flex 和 Grid 布局在不同浏览器、不同 ES 版本下的兼容性问题

- **问题描述:** `flex` 和 `grid` 在实际项目中有哪些兼容性问题？如果浏览器比较老，或者项目要兼容低版本环境，该怎么处理？
- **我的解答:**
  这个问题我会先澄清一点：**`flex` 和 `grid` 是 CSS 布局规范，和 ES5 / ES6 不是同一层面的东西**。  
  ES 版本主要影响的是 JavaScript 语法兼容，`flex/grid` 主要受**浏览器 CSS 实现能力**影响。但在真实项目里，这两件事经常一起被问，因为它们都属于“前端兼容性”。

  1. **Flex 的兼容性整体比 Grid 好**：
  - `flex` 在现代浏览器支持已经非常成熟，Chrome、Edge、Firefox、Safari 基本没问题。
  - 但在一些老浏览器，尤其是 **IE10/IE11**，会有历史版本语法和实现差异，比如早期需要 `display: -ms-flexbox;`，某些属性行为也不完全一致。
  - 常见问题包括：`flex: 1` 计算不一致、`min-height`/`overflow` 组合异常、百分比高度场景表现不一致。

  2. **Grid 的兼容性比 Flex 差很多**：
  - 现代浏览器基本支持 `grid`
  - 但 **IE 基本不支持现代 Grid 规范**，只有一套很早期的 `-ms-grid` 实现，语法复杂且和现代 `grid-template-columns`、`grid-area` 等写法差异很大
  - 所以如果项目需要兼容 IE，一般**不建议把 Grid 作为核心布局方案**

  3. **真实项目里的处理策略**：
  - **如果兼容现代浏览器**：`flex` 和 `grid` 都可以放心用，`grid` 特别适合二维布局，`flex` 适合一维布局
  - **如果要兼容 IE11 或更老环境**：优先选 `flex`，复杂场景退回传统布局方案，比如 `float`、`inline-block`，或者做降级布局
  - **关键页面做兼容兜底**：比如用 `@supports (display: grid)` 做能力检测，支持就走 `grid`，不支持就降级成 `flex`

  ```css
  .layout {
    display: flex;
  }

  @supports (display: grid) {
    .layout {
      display: grid;
      grid-template-columns: 1fr 1fr;
    }
  }
  ```

  4. **工程化层面的兼容处理**：
  - `Autoprefixer` 可以给部分 CSS 自动补浏览器前缀，比如 `-webkit-`、`-ms-`
  - 但它**不能把现代 Grid 完整无损地转成所有老浏览器都能工作的写法**
  - 所以工程化工具能解决一部分兼容问题，但不能完全替代布局方案本身的选型

  5. **和 ES 版本的关系怎么回答更稳**：
  - 如果面试官把“浏览器兼容”和“ES 兼容”放一起问，我会说：
    - **ES 兼容**：靠 `Babel`、`core-js`、polyfill 解决 JS 语法和 API 问题
    - **CSS 布局兼容**：靠 `Autoprefixer` + 降级方案 + 浏览器能力检测解决
  - 两者都属于兼容性，但处理手段完全不同

  **一句话总结：**
  - `flex`：现代浏览器稳定，老浏览器有细节坑，但可控
  - `grid`：现代浏览器很好用，但老浏览器尤其 IE 兼容性差，项目里要谨慎选型
  - ES 和布局兼容不是一回事，回答时要主动把这层关系讲清楚

- **知识点标签:** #Flex #Grid #浏览器兼容性 #Autoprefixer #前端工程化
