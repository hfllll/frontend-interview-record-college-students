### ❓ 问题 1：uni-app 和微信原生开发小程序的优缺点

- **问题描述:** 如果都能做小程序，为什么有的团队选 uni-app，有的团队选微信原生？两者分别适合什么场景？
- **我的解答:**
  我会从**开发效率、性能、跨端能力、生态限制**四个角度来回答：

  1. **uni-app 的优点**：
  - **一套代码多端复用**，可以同时覆盖微信小程序、H5、App，适合人力有限、项目要多端同步推进的团队。
  - Vue 语法更友好，前端上手成本低，组件化和工程化体验更接近 Web 开发。
  - 对已有 Vue 技术栈团队很友好，迁移成本小，开发效率高。

  2. **uni-app 的缺点**：
  - 本质上有一层框架封装，遇到复杂场景时，性能和调试体验通常不如原生直接。
  - 某些平台特有能力、原生 API、兼容性问题，需要写条件编译或平台适配代码。
  - 出现底层 bug 时，排查链路更长，要区分是业务问题、框架问题还是平台问题。

  3. **微信原生小程序的优点**：
  - **性能和兼容性更稳定**，因为直接贴着微信官方规范开发，没有额外抽象层。
  - 官方 API、订阅消息、支付、开放能力等支持通常最及时。
  - 对页面级细节优化、复杂交互、平台能力深度使用场景更合适。

  4. **微信原生小程序的缺点**：
  - 只能做微信端，**跨端复用能力差**，如果后续要扩 H5 或 App，重复开发成本高。
  - 工程化和组件生态不如 Vue 技术栈自然，团队协作效率通常低于成熟前端工程体系。

  **总结：**
  如果项目目标是**快速上线、多端复用、团队本身偏 Vue 技术栈**，我会优先选 uni-app；如果项目是**深度依赖微信生态、追求极致性能和稳定性**，原生会更合适。

- **知识点标签:** #uniapp #微信小程序 #跨端开发 #技术选型

### ❓ 问题 2：文件上传到 OSS，如何和后端配合做断点续传？

- **问题描述:** 大文件上传到 OSS 时，如果网络中断或用户切后台，如何避免重新从 0 开始传？前端和后端一般怎么配合？
- **我的解答:**
  这个问题本质上是**分片上传 + 上传状态记录 + 失败后续传**。

  1. **前端先切片**：
  前端拿到文件后，不是整文件直接传，而是按固定大小切成多个 chunk，比如每片 2MB 或 5MB。这样中断后只需要补传失败的分片，而不是整文件重传。

  2. **先向后端申请上传会话**：
  前端先把文件名、文件大小、文件 hash 传给后端，后端生成一个 `uploadId` 或上传任务 ID，并返回当前已经上传成功的分片列表。
  这里的文件 hash 很关键，它可以唯一标识这个文件，后端也能借它做**秒传判断**。

  3. **前端并发上传分片到 OSS**：
  常见有两种方式：
  - **服务端中转上传**：前端把分片传给后端，由后端再传 OSS。优点是安全、统一；缺点是吃后端带宽。
  - **前端直传 OSS**：后端给前端签名或临时凭证，前端直接把 chunk 传到 OSS。这样链路更短，后端压力更小，企业里更常见。

  4. **后端记录每个分片状态**：
  每上传成功一个 chunk，前端把分片序号、uploadId、ETag 等信息回传后端，后端落库或写 Redis，记录哪些片已经成功。

  5. **断点续传**：
  如果网络断了，用户重新进入页面时，前端再次拿文件 hash 去问后端：这个文件之前上传到哪了？后端返回已完成分片列表，前端只补传缺失部分。

  6. **全部成功后合并**：
  所有 chunk 上传完成后，前端通知后端执行“合并分片”或“完成 multipart upload”，OSS 最终生成完整文件。

  **补充两个面试加分点：**
  - **秒传**：如果后端根据文件 hash 发现这个文件已存在，直接返回上传成功，不再重复传。
  - **并发控制**：上传不能无限并发，一般限制 3 到 5 个 chunk 同时传，避免把带宽和浏览器连接数打满。

  **一句话总结：**
  断点续传不是某一个 API，而是一整套机制：**前端切片、后端记录状态、失败后按缺失分片补传**。

- **知识点标签:** #OSS #文件上传 #分片上传 #断点续传

### ❓ 问题 3：电商平台并发下库存不足，却仍被重复下单，怎么解决？

- **问题描述:** 假设商品只剩 1 件，但很多请求同时过来都判断“还有库存”，结果被超卖了。这个问题怎么解决？
- **我的解答:**
  这个问题本质上是高并发下的**库存超卖**，核心不在前端，而在后端的并发控制。但前端也要理解整体链路。

  1. **数据库层原子扣减库存**：
  不能先查库存再减库存，因为这两个动作分开就会有并发窗口。正确做法是直接执行原子更新，例如：

  ```sql
  update goods
  set stock = stock - 1
  where id = ? and stock > 0;
  ```

  如果影响行数为 1，说明抢到库存；如果为 0，说明库存不足。这样能从数据库层防止超卖。

  2. **乐观锁 / 版本号机制**：
  在库存表中加 `version` 字段，更新时带上旧版本号：

  ```sql
  update goods
  set stock = stock - 1, version = version + 1
  where id = ? and version = ? and stock > 0;
  ```

  如果版本不匹配，说明并发冲突，本次下单失败或重试。

  3. **Redis 预扣库存 + MQ 削峰**：
  如果是秒杀这类高并发场景，直接打数据库会扛不住。通常会先在 Redis 中预扣库存，扣成功的请求进入消息队列异步下单，后端再做最终一致性校验。这样可以先挡住流量高峰。

  4. **幂等控制，防止重复提交**：
  用户可能因为网络慢连续点多次“立即购买”，所以除了库存问题，还要防重复下单。常见做法是：
  - 前端按钮点击后立即置灰、loading，防止重复触发。
  - 后端基于用户 ID + 商品 ID + 业务流水号做幂等校验，同一请求只能成功一次。

  5. **分布式锁只作为补充，不是首选**：
  可以用 Redis 锁控制同一商品同一时刻只允许一个线程扣库存，但锁会带来性能和复杂度问题。一般优先用**数据库原子更新 / 乐观锁 / Redis 预扣**，锁只是特殊场景兜底。

  **总结：**
  - 普通电商并发：数据库原子扣减 + 幂等控制
  - 高并发秒杀：Redis 预扣库存 + MQ 削峰 + 最终一致性
  - 前端侧：按钮防重复点击，避免把无意义请求继续放大

- **知识点标签:** #库存超卖 #高并发 #乐观锁 #Redis #幂等
